# 本地知识库最小链路：embedding + 检索 + 回答

## 本质

这篇文档要解决的不是“如何搭一个完整 RAG 系统”，而是更小的一个问题：

在本地环境里，怎样把：

- 文档
- embedding 模型
- 检索逻辑
- chat 模型

串成一个最小可理解、最小可解释的闭环。

如果只记一句话，可以记成：

> embedding 负责把文本变成向量，检索负责从向量里找相关内容，chat 模型负责把相关内容组织成最终回答。

---

## 原理

一个最小知识库链路，通常分成三段职责：

### 1. embedding：负责“转向量”

无论是你的文档，还是用户提出的问题，想要做语义相似度比较，首先都要被转换成向量。

所以 embedding 模型做的事情不是“回答问题”，而是：

- 把文档片段编码成向量
- 把用户问题编码成向量

这样后面才能比较它们是否接近。

### 2. 检索：负责“找相关内容”

当你已经有：

- 文档向量
- 问题向量

就可以做相似度计算。  
最简单的思路是：

- 让问题向量和所有文档向量逐个比较
- 找出最接近的前几个片段

这一步的产出不是最终答案，而是“最可能相关的原始内容”。

### 3. chat 模型：负责“组织最终回答”

当你拿到了最相关的文档片段之后，再把这些片段连同用户问题一起交给 chat 模型。

chat 模型此时做的不是“自己凭空想答案”，而是：

- 阅读召回片段
- 基于这些片段组织语言
- 给出更像最终答复的自然语言结果

所以最小链路里，三者关系可以简单记成：

- embedding：编码
- 检索：召回
- chat：回答

---

## 流程

把最小链路按数据流拆开看，通常就是四步。

### 第一步：文档切分

原始资料往往不是一整块直接拿来算 embedding，而是先切成更小的片段。

例如一篇文档可以切成：

- 段落
- 小节
- 固定长度文本块

为什么要先切分：

- 太长的文本不利于精确检索
- 你真正想召回的，通常是某个局部片段，不是整篇文档

所以这一步的目标不是“切得越碎越好”，而是让每个片段都还能保持基本语义完整。

### 第二步：文档向量化

把每个文档片段送进 embedding 模型，得到一组向量。

可以把它理解成：

```text
片段A -> 向量A
片段B -> 向量B
片段C -> 向量C
```

此时你得到的是“知识库的向量表示”。

### 第三步：问题向量化并检索

当用户提问时，也要把问题送进同一个 embedding 模型，得到问题向量。

例如：

```text
用户问题 -> 问题向量Q
```

然后用 `Q` 去和之前保存的文档向量做相似度比较。  
最简单的逻辑是：

- 逐个比较相似度
- 排序
- 取前 `Top-K` 个结果

这一步产出的是：

- 最相关的若干文档片段
- 而不是最终自然语言答案

### 第四步：把召回片段交给 chat 模型回答

当你拿到 `Top-K` 片段后，就可以把它们拼进提示词。

最直观的形式可以理解成：

```text
已检索到的资料：
片段1
片段2
片段3

用户问题：
XXX

请只基于以上资料回答。
```

然后把这段提示词交给 chat 模型，由它生成最终自然语言结果。

到这里，一个最小知识库闭环才算真正完成：

```text
文档 -> embedding -> 文档向量
问题 -> embedding -> 问题向量
问题向量 vs 文档向量 -> 检索出 Top-K 片段
Top-K 片段 + 用户问题 -> chat 模型 -> 最终回答
```

## 示例

下面用一个极简例子把这个过程串起来。

### 例子：两段资料回答“什么是操作系统”

假设你有两段资料：

```text
文档A：操作系统负责管理硬件资源，并为应用程序提供基础运行环境。
文档B：编译器负责把高级语言转换成机器可执行形式。
```

第一步，先做文档向量化：

```text
文档A -> embedding -> 向量A
文档B -> embedding -> 向量B
```

第二步，用户提问：

```text
问题：什么是操作系统？
问题 -> embedding -> 问题向量Q
```

第三步，做相似度比较：

```text
Q vs 向量A -> 相似度高
Q vs 向量B -> 相似度低
```

于是你会检索到：

```text
Top-1 = 文档A
```

第四步，把检索结果交给 chat 模型：

```text
资料：
操作系统负责管理硬件资源，并为应用程序提供基础运行环境。

问题：
什么是操作系统？

请基于资料回答。
```

此时 chat 模型再生成最终回答，例如：

```text
操作系统是一类负责管理硬件资源，并为应用程序提供基础运行环境的软件。
```

这个例子里最关键的理解是：

- embedding 没有直接回答
- 检索也没有回答
- 真正输出自然语言的是 chat 模型

### 最小命令视角下怎么理解

如果你站在 `llama.cpp` 命令行角度去理解，也可以先粗略看成：

```text
1. 用 llama-embedding 把文档转成向量
2. 用 llama-embedding 把问题转成向量
3. 在你自己的检索逻辑里比较相似度
4. 把检索出的文本片段交给 llama-cli 或 llama-server 对应的 chat 模型
```

这里最容易混淆的一点是：

- `llama.cpp` 提供的是模型运行能力
- “怎么存向量、怎么算相似度、怎么拼上下文” 这些流程逻辑，需要你自己设计或接入别的组件

## 扩展建议

这篇文档只覆盖最小闭环，不覆盖下面这些更完整的工程能力：

- 向量数据库
- reranker
- 多路召回
- 知识库更新策略
- 服务化 API

也就是说，它的目标只是先让你建立正确分工：

- embedding 不是回答模型
- 检索不是回答模型
- chat 模型不负责自己找资料

如果你准备继续往真正可用的本地知识库演进，下一步建议按这个顺序扩展：

1. 先实现一个最简单的“文本切分 + 向量保存 + 相似度排序”脚本
2. 再补 reranker，优化召回质量
3. 再引入向量数据库，解决规模化存储和检索问题
4. 最后再做服务化接口和前端交互

如果前面这层分工没有搞清楚，后面即使接了更多框架，也很容易只是“把组件堆起来”，而不是理解整个链路。
