# Linux DNS、resolvconf 与 dhclient 排障

## 本质

Linux 上域名解析失败时，先区分“IP 连通性”和“DNS 解析”。如果 `ping 8.8.8.8` 正常，但访问 `github.com` 报 `Could not resolve host`，问题通常不在 Git、HTTPS 或目标仓库，而在 DNS 解析链路。

最终判断以 `/etc/resolv.conf` 为准，但这个文件不一定应该手工编辑。很多系统会通过 `resolvconf`、NetworkManager、systemd-resolved、ifupdown 或 DHCP 客户端动态生成它。

## 基本链路

```text
网络接口获取地址
  -> DHCP 客户端获得网关和 DNS
  -> resolvconf / 网络管理服务汇总 DNS
  -> 生成 /etc/resolv.conf
  -> glibc resolver 解析域名
  -> git / curl / apt 等程序访问域名
```

## 最小判断

```bash
ping -c 2 8.8.8.8
getent hosts github.com
cat /etc/resolv.conf
```

含义：

- `ping 8.8.8.8` 成功：IP 出口基本正常。
- `getent hosts github.com` 失败：系统默认 DNS 解析失败。
- `/etc/resolv.conf` 里的 `nameserver` 才是当前 glibc resolver 实际使用的 DNS 入口。

如果系统安装了 `nslookup` 或 `dig`，可以直接指定 DNS 验证：

```bash
nslookup github.com 8.8.8.8
```

如果指定 `8.8.8.8` 能解析，而默认解析失败，问题基本在本机 DNS 配置生成链路。

## dhclient 配置

`supersede domain-name-servers` 是 `dhclient.conf` 配置语句，不是 shell 命令。它应写入：

```bash
sudo vim /etc/dhcp/dhclient.conf
```

示例：

```conf
supersede domain-name-servers 8.8.8.8, 114.114.114.114;
```

然后重新获取 DHCP 租约或重启网络服务，例如：

```bash
sudo dhclient -r
sudo dhclient
```

或在使用传统 networking 服务时：

```bash
sudo systemctl restart networking
```

具体命令取决于系统实际由哪个服务管理网络。

## resolvconf 注意点

如果 `/etc/resolv.conf` 顶部出现：

```text
# Dynamic resolv.conf(5) file for glibc resolver(3) generated by resolvconf(8)
#     DO NOT EDIT THIS FILE BY HAND -- YOUR CHANGES WILL BE OVERWRITTEN
```

说明直接编辑 `/etc/resolv.conf` 不可靠，下一次网络刷新会覆盖。

此时要么修改上游输入源，例如 DHCP 客户端配置；要么按当前系统的 `resolvconf` 规则配置静态 DNS。修改后必须重新触发生成，并检查最终文件：

```bash
sudo resolvconf -u
cat /etc/resolv.conf
```

如果结果没有变化，说明修改点不是当前生成链路的有效输入源，需要继续查真正的网络管理组件。

## 个人理解

DNS 排障不要一上来改文件，要先看数据流：

1. 机器能不能访问公网 IP。
2. 系统默认 resolver 能不能解析域名。
3. `/etc/resolv.conf` 当前到底写了哪些 DNS。
4. 谁在生成 `/etc/resolv.conf`。
5. 应该改生成源头，而不是改生成结果。

对嵌入式板卡尤其要注意：镜像可能比较旧，`resolvconf`、`dhclient`、路由器下发 DNS、IPv6 DNS 和传统网络脚本可能同时参与。最终只认一个结果：应用程序实际读取到的 `/etc/resolv.conf`。
