# 本地大模型部署硬件估算

## 本质

本地部署大模型时，真正限制机器的通常不是“能不能下载模型”，而是运行时能否同时容纳三类内存开销：

1. 模型权重
2. KV cache
3. 推理框架和系统运行时开销

所以判断一台机器能不能跑某个模型，要同时看参数规模、量化格式、上下文长度、显存、内存和推理框架。

## 原理

### 1. 参数量决定基础权重体积

粗略估算：

- FP16 / BF16：每个参数约 2 字节
- INT8：每个参数约 1 字节
- Q4：每个参数约 0.5 字节，再加少量量化元数据

因此 12B 模型仅权重大致可以这样估：

- FP16：约 24GB 起步
- INT8：约 12GB 起步
- Q4：约 6GB 到 8GB

这只是权重，不包括上下文缓存。

### 2. 上下文长度会影响 KV cache

上下文越长，KV cache 越大。  
同一个 12B Q4 模型，`4K context` 和 `32K context` 的显存压力可能完全不同。

因此第一次验证模型时，不要直接开最大上下文。应先用较小上下文确认模型能稳定加载和生成。

### 3. GPU 显存不够时可以混合推理

以 `llama.cpp` 为例，可以用 `-ngl` 控制放到 GPU 的层数：

```bash
llama-cli \
  -m /path/to/model.gguf \
  -ngl 20 \
  -c 4096 \
  -p "请解释什么是 Binder"
```

`-ngl` 越高，GPU 参与越多，速度通常越快，但显存占用也越高。  
如果加载失败或显存爆掉，可以降低 `-ngl` 或上下文长度。

## 流程

判断一台机器适合什么模型，可以按下面顺序：

1. 看显存：决定能否全量 GPU 加速。
2. 看系统内存：决定是否能 CPU/GPU 混合推理。
3. 看模型量化：优先从 Q4 或 Q5 开始。
4. 看上下文长度：先小上下文验证，再逐步增加。
5. 看实际速度：能跑不等于好用。

## 常见判断

以 8GB 显存、60GB 级别内存的 Linux 笔记本为例：

- 4B / 7B Q4：通常适合，体验较稳。
- 8B Q4 / Q5：通常适合。
- 12B Q4：可以尝试，可能需要控制上下文或部分 CPU offload。
- 12B FP16：不适合完整放入 8GB 显存。
- 27B / 31B Q4：系统内存可能能加载，但速度和体验通常不适合日常交互。

## 问题

### 1. 为什么模型文件小于显存，仍然可能爆显存？

因为模型文件大小不等于运行时总占用。推理时还需要 KV cache、计算 buffer、CUDA/cuBLAS 后端开销以及桌面环境占用。

### 2. 为什么同一个模型别人能跑，我这里不能跑？

常见差异包括：

- 量化格式不同
- 上下文长度不同
- GPU offload 层数不同
- 推理后端不同
- 显卡上已有其他进程占用显存

### 3. 为什么 CPU/GPU 混合推理能跑但慢？

因为部分层在 CPU 上计算，且 CPU 与 GPU 之间存在数据传输和同步成本。混合推理解决的是“能加载”，不保证“速度舒服”。

## 个人理解

本地部署大模型要把“能跑”拆成三层：

1. 能加载：内存和显存不爆。
2. 能生成：推理链路正常。
3. 好用：速度、上下文、稳定性满足真实任务。

学习阶段优先追求链路跑通，不必一开始追最大参数。对 8GB 显存机器来说，4B 到 12B 量化模型是更合理的实验区间。
