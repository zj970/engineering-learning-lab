# AI 编码代理选型：Codex、Claude Code、Gemini CLI

## 本质

比较 AI 编码工具时，最容易犯的错是只问“哪个最强”，却不先问“它到底是怎么工作的”。

这类工具至少要先分三类：

- 远程异步代理：任务交给云端独立环境，适合并行外包。
- 本地终端代理：直接在当前仓库里读文件、改代码、跑命令。
- 生态集成代理：除了编码，还强绑定搜索、插件、云账号或工作流。

所以真正的选型问题不是“模型 PK”，而是：

> 你的工作流更需要本地交互，还是远程委托；更需要透明过程，还是更强平台集成。

---

## 原理

### 1. Codex：偏远程异步代理

OpenAI 官方把 Codex 描述为 `cloud-based software engineering agent`。它的核心特征不是“在你终端里陪你写”，而是：

- 每个任务在独立云端沙箱里跑
- 可以并行分配多个任务
- 能读写仓库、跑测试、给出终端日志和验证证据
- 能读取仓库里的 `AGENTS.md` 作为项目协作规范

这意味着它更像“可委派的远程工程同事”，适合：

- 让它后台修 bug
- 让它批量写测试
- 让它解释代码库
- 让它处理较独立的实现任务

它不一定是最适合高频小改动的第一选择，但很适合异步卸载工作量。

### 2. Claude Code：偏本地终端 + 多入口协同

Anthropic 官方把 Claude Code 放在 terminal、IDE、Slack、web 等多个入口里使用。

它的强项在于：

- 更像日常开发工作台的一部分
- 既能终端使用，也能挂到 IDE 或团队协作入口
- 当前官方页面已经把 `desktop / VS Code / JetBrains / web / Slack` 都列为可用入口

这说明它的产品思路不是单一 CLI，而是“同一个代理，挂在多个开发触点上”。

如果你想要的是：

- 一边看代码一边让代理改
- 在 IDE 中持续来回调整
- 团队里把编码、协同、例行任务打通

那 Claude Code 的工作流会更顺手。

### 3. Gemini CLI：偏开源终端代理 + Google 生态

Google 官方仓库把 Gemini CLI 定义为 `open-source AI agent`，强调：

- terminal-first
- 内置文件操作、shell、web fetch
- 内置 `Google Search grounding`
- 支持 `MCP`
- 支持 `GEMINI.md`
- 支持 `Plan mode`、`subagents`、`sandboxing`

它更像一个可扩展的终端代理平台，而不是单纯聊天壳。

但这里有一个非常重要的时效点：

- 官方文档首页横幅明确写着，`2026-06-18` 起，`unpaid tier` 和 `Google One` 用户的 `Gemini CLI` 将被 `Antigravity CLI` 替代。

所以如果你是个人用户，不能只看 GitHub 热度，还要看你准备走哪条账号与配额路径。

## 流程

面对这类工具，建议按下面顺序选：

### 第一步：先判断你的工作模式

如果你经常要：

- 把任务丢后台
- 同时开多个实现分支
- 希望它自己跑测试、整理结果

优先看 `Codex` 这类远程异步代理。

如果你经常要：

- 在本地仓库里边看边改
- 高频试错
- 手工接管和追问很多

优先看 `Claude Code` 或 `Gemini CLI` 这类终端代理。

### 第二步：再看你是否依赖生态

- 强依赖 OpenAI 工作流和远程代理体验：看 `Codex`
- 强依赖 IDE / Slack / 多端协作：看 `Claude Code`
- 强依赖开源、MCP、Google 搜索和终端扩展：看 `Gemini CLI`

### 第三步：最后才看价格与配额

很多人一开始先比价格，但实际上：

- 工作模式不匹配，再便宜也会低效
- 配额再高，指令透明度不够也不利于学习
- 对学习者来说，“能不能看懂它为什么这么做” 比 “一次能跑多大活” 更重要

## 常见问题

### 1. 这几个东西本质上都是一个东西吗？

不是。

它们都属于 AI 编码代理，但产品形态不同：

- `Codex` 更像远程委派型工程代理
- `Claude Code` 更像开发工作台中的协作代理
- `Gemini CLI` 更像开源终端代理框架

### 1.1 `OpenCode` 能放进这个比较里吗？

可以。

`OpenCode` 官方首页直接把自己定义为 `The open source AI coding agent`，并说明它可以运行在 `terminal`、`IDE`、`desktop`，还能连接 Claude、GPT、Gemini 等不同模型。

因此它和 `Codex / Claude Code / Gemini CLI` 是同一大类产品，差别主要在：

- 是否开源
- 是否更强调本地终端
- 是否更强调多模型接入
- 是否更强调平台生态或远程异步能力

如果只看定位，我会把它先归到：

- 偏本地终端代理
- 偏开源
- 偏多模型聚合

### 1.2 `Pi` 能和这些编码代理放一起比吗？

通常不能。

如果这里的 `Pi` 指的是 `Inflection AI` 的 `Pi`，那它的官方定位更接近 personal AI / emotionally intelligent AI。Inflection 官网强调的是：

- human-centered
- emotionally intelligent
- `Talk to Pi`
- voice on your favorite device

这说明它的目标更偏：

- 个人对话
- 情感支持
- 语音交互
- 日常陪伴式助手

而不是：

- 读仓库
- 改代码
- 跑命令
- 执行工程任务

所以 `Pi` 和 `Codex / Claude Code / Gemini CLI / OpenCode` 不是同一类产品。前者更像个人 AI 助手，后者才是 AI 编程代理。

### 2. 学习工程能力，应该优先用哪个？

如果你的目标是提升命令行、仓库理解、测试意识、问题拆解能力，优先使用“过程暴露更充分”的终端代理更合适。

原因很直接：

- 你能看到它读了哪些文件
- 你能看到它执行了什么命令
- 你能看到它如何计划和验证

这比只拿最终答案更适合成长。

### 3. 为什么不能只看模型排行？

因为真实开发里，效率往往由下面这些因素决定：

- 能不能直接读当前仓库
- 能不能安全跑命令
- 能不能并行处理任务
- 能不能接入 IDE、GitHub、Slack、MCP
- 能不能让你追踪执行证据

这些因素常常比模型榜单更影响体验。

## 个人理解

如果把它们放到工程实践里，我会这样理解：

- `Codex` 适合“把一块活完整委派出去”
- `Claude Code` 适合“把代理嵌进日常开发循环”
- `Gemini CLI` 适合“把终端代理当可扩展平台来折腾和集成”

对仍在成长中的工程师，不要先追“最强模型”，而要先追：

1. 我能不能看懂代理的行为链路。
2. 我能不能验证它的结果。
3. 我能不能在它出错时及时接管。

只有先把这三点建立起来，AI 工具才是在放大你的能力，而不是替你掩盖短板。
