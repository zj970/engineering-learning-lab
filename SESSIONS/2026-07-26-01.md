---

## 问题

`ifconfig` 显示 `FlClash`、多个 `br-*`、`docker0`、`enp4s0` 和大量 `veth*`，哪些接口实际在使用？

---

## 分析

`enp4s0` 是宿主机物理以太网接口，地址为 `192.168.51.12/24`，累计接收约 2.4 GiB，是局域网和底层网络出口。`FlClash` 是 FlClash 创建的 TUN 虚拟接口，使用保留给基准测试的 `198.18.0.0/15` 地址空间，累计接收约 2.3 GiB，说明代理接管了大量流量。

`br-*` 是 Docker 用户自定义 bridge 网络，名称后半段通常对应 Docker network ID 的前 12 位；`docker0` 是 Docker 默认 bridge。带有 `RUNNING` 且有收发计数的 `br-2368c857ae9c`、`br-5591739dcf62`、`br-bfba6392aac7` 和 `docker0` 至少连接过活动端点；只有 `UP`、没有 `RUNNING` 且收发为 0 的其余 bridge 当前大概率没有运行容器接入。

`veth*` 是容器侧网卡在宿主机上的对端。它们负责把容器接到对应 bridge，不是额外的物理网卡。`lo` 是本机回环接口，供本机进程通过 `127.0.0.1` 或 `::1` 通信。

流量计数是接口创建或系统启动以来的累计值，只能证明过去使用过。判断当前使用情况，应结合路由选择和短时间内计数是否增长。`UP` 只表示管理状态已启用，`RUNNING` 通常表示底层链路或虚拟端点可用，也不等于正在持续传输。

`enp4s0` 的 `RX dropped 22950` 值值得继续观察，但不能仅凭累计值判定当前丢包。应采样其增长速度，并使用 `ethtool -S enp4s0` 区分驱动、硬件和内核队列统计。

补充检查显示 `br-ad78514d95df`、`br-bd81967e3e1b`、`br-9006ab345f48` 和 `br-a3d7bc6506ac` 均处于 `DOWN`、`NO-CARRIER`，但仍带有管理状态 `UP`。这通常表示 Docker 网络对象仍然存在，只是当前没有活动 veth 端点。它们可以作为清理候选，但需要先通过 `docker network inspect` 确认网络名称、Compose 标签和容器引用；删除时应使用 `docker network rm`，不能直接用 `ip link delete` 绕过 Docker 的状态管理。

---

## 关键知识点

- 一个数据包可能依次经过应用、`FlClash` TUN、策略路由、`enp4s0`，所以多个接口同时增长并不代表有多个物理出口。
- `br-*`、`docker0` 和 `veth*` 共同组成 Docker 的二层虚拟网络。
- `UP`、`RUNNING`、配置了 IP、位于路由中、当前有流量是五种不同状态。
- `ip route get <目标地址>` 比单看 `ifconfig` 更适合判断某个目标实际使用哪个接口。
- RX/TX 是接口视角：接收进入该接口的是 RX，从该接口送出的是 TX。

## 收获

- 当前主要链路是 `FlClash` 与 `enp4s0`，前者负责代理隧道，后者负责实际局域网传输。
- 多个 `br-*` 和 `veth*` 来自 Docker，它们属于内部网络基础设施，不是多块真实网卡。
- 可以通过连续采样计数器判断接口是否此刻有流量，通过路由查询判断指定目标走哪个接口。
