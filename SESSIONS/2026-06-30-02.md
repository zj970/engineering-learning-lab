# 会话记录

## 基本信息

- 时间：2026-06-30
- 主题：VS Code 在 KDE Wayland 下 Fcitx5/Rime 输入法样式异常与粘贴失败排查

---

## 问题

用户反馈：

- 终端输入法正常，但 VS Code 中输入法候选框变成另一种样式。
- 从浏览器复制的文字无法粘贴到 VS Code。
- 手动使用 `code --ozone-platform=wayland --enable-wayland-ime` 后仍不正常，并出现 `Warning: 'enable-wayland-ime' is not in the list of known options, but still passed to Electron/Chromium.`
- 需要检查当前 VS Code 启动配置或个人配置。

---

## 分析

本次排查先确认 VS Code 启动链路：

- `code` 实际路径是 `/usr/bin/code`。
- `/usr/bin/code` 会读取 `~/.config/code-flags.conf`，并把其中参数追加到 `/usr/share/code/bin/code`。
- 当前 `~/.config/code-flags.conf` 不存在。
- `~/.vscode/argv.json` 未配置 Wayland/IME 参数。
- `/usr/share/applications/code.desktop` 的 `Exec=code %F` 未带 Wayland/IME 参数。
- 当前 VS Code 版本是 `1.126.0`，Electron 日志显示 `ver=42.2.0`。

宿主进程检查显示：

- 当前 VS Code 主进程确实以 `/usr/share/code/code --ozone-platform=wayland --enable-wayland-ime` 启动。
- KDE 会话是 Wayland：`XDG_SESSION_TYPE=wayland`，`XDG_CURRENT_DESKTOP=KDE`。
- Fcitx5 变量存在：`GTK_IM_MODULE=fcitx`、`QT_IM_MODULE=fcitx`、`XMODIFIERS=@im=fcitx`。

用户日志显示两类异常：

- 启动阶段存在两个 Fcitx5 实例竞争 DBus 名称：后启动的 `fcitx5[1843]` 报 `Unable to request dbus name. Is there another fcitx already running?` 后卸载插件并退出。
- KWin 在 22:49:28 和 22:49:59 报 `Incoming X selection conversion failed`，这与浏览器到 VS Code 的剪贴板/selection 桥接失败相符。

Rime 侧还看到：

- `~/.config/fcitx5/crash.log` 有 librime 部署阶段调用栈。
- 当前用户日志里有 `warning: config does not conform to schema: document path "/conversion_chain/0/dict"`，说明 Rime 配置仍有 schema 不匹配风险。

---

## 关键知识点

- VS Code 的 `--enable-wayland-ime` 警告不等价于参数完全无效；它表示 VS Code CLI 不认识该参数，但仍会传给 Electron/Chromium。
- Arch 的 `/usr/bin/code` 支持通过 `~/.config/code-flags.conf` 固化启动参数；只在命令行临时传参不能保证桌面图标、URL handler、已有窗口复用时一致。
- KDE Wayland 下输入法链路至少包含：KWin/Wayland 文本输入协议、Fcitx5 DBus 名称、Rime 插件、Electron Ozone 平台、XWayland selection 桥接。
- “终端正常、VS Code 异常”通常不是单点问题，应先区分应用是否走 Wayland 原生、XWayland、GTK/Qt IM module 或 Electron 文本输入协议。

---

## 我的薄弱点

- 容易把沙箱内 `fcitx5-diagnose` 的“看不到宿主进程”误判为宿主 Fcitx5 未运行；需要用宿主 `ps`、用户日志、DBus 名称一起确认。
- 对 Wayland/XWayland 剪贴板 selection 桥接问题需要结合 KWin 日志判断，不能只看 VS Code 自身日志。

---

## 收获

- 当前 VS Code 的长期启动配置未固化 Wayland/IME 参数；当前进程虽然临时带了参数，但桌面入口仍可能不一致。
- Fcitx5 当前存在重复启动/DBus 名称竞争证据，应该作为输入法样式不稳定的重点方向。
- 浏览器复制到 VS Code 粘贴失败有 KWin `Incoming X selection conversion failed` 直接日志证据，倾向于 Wayland/XWayland 剪贴板桥接问题。

---

## 处理结果

- 已创建 `~/.config/code-flags.conf`，内容为：

```text
--ozone-platform=wayland
--enable-wayland-ime
```

- 已创建 `~/.config/autostart/org.fcitx.Fcitx5.desktop`，通过 `Hidden=true` 禁用 XDG autostart 中重复的 Fcitx5 启动入口。
- 保留 `~/.config/kwinrc` 中的 KWin Wayland InputMethod 配置：

```text
[Wayland]
InputMethod[$e]=/usr/share/applications/org.fcitx.Fcitx5.desktop
VirtualKeyboardEnabled=true
```

- 未强制关闭正在运行的 VS Code，避免影响未保存编辑器状态；需要用户退出所有 VS Code 窗口后重新打开。
- Fcitx5 重复启动修复需要重新登录后验证。
- 用户进一步澄清主要问题是候选框配色：终端为灰色，VS Code 为蓝色。已将 `~/.config/fcitx5/conf/classicui.conf` 中 `UseAccentColor=True` 改为 `UseAccentColor=False`，使 Classic UI 不再跟随 KDE/应用强调色。
- 已执行 `fcitx5-remote -r` 重新加载 Fcitx5 配置；当前日志显示 `classicui`、`kimpanel`、`rime` 均已加载，VS Code 进程仍带 `--ozone-platform=wayland --enable-wayland-ime`。
