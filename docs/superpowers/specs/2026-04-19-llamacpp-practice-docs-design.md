# llama.cpp 实操补充文档设计说明

**目标：** 在保留现有 `llama.cpp` 入门指南不变的前提下，新增两篇面向实操的独立知识文档，一篇用于常用命令速查，一篇用于说明本地知识库的最小链路。

**读者画像：**
- 已完成 `llama.cpp` 基础安装与环境配置
- 知道 `chat / coder / embedding` 三类模型的基本区别
- 能在 Linux 终端执行命令
- 需要一份更贴近“下一步怎么做”的实操参考

**范围：**
- 新增 `llama.cpp` 常用命令速查文档
- 新增“本地知识库最小链路：embedding + 检索 + 回答”文档
- 保持现有入门指南不改写、不重构
- 明确两篇文档的定位、结构和边界

**非目标：**
- 不重写 `llama.cpp` 入门指南
- 不展开成完整 RAG 系统工程实践
- 不引入向量数据库、Web 框架或前端界面
- 不覆盖所有 `llama.cpp` 参数和全部工具

---

## 1. 背景

当前仓库中已经有一篇：

- `KNOWLEDGE/Tools/llama.cpp-入门指南.md`

它负责解释：

- `llama.cpp` 是什么
- 模型类型怎么区分
- `GGUF`、量化、`-ngl`、`PATH`、`LD_LIBRARY_PATH` 等核心概念

这篇文档解决的是“建立整体认知”的问题，但还没有覆盖两个高频实操场景：

1. 平时最常用的命令到底该怎么写
2. 知识库最小链路里，embedding、检索、回答之间到底怎么串起来

因此需要补两篇新的独立文档，用来承接“会一点概念之后，怎么开始真正使用”的阶段。

## 2. 方案比较

### 方案 A：把新内容直接追加进入门指南

优点：
- 文件少
- 入口集中

缺点：
- 容易把入门指南写成大杂烩
- 后续继续补充时层次会越来越乱
- “概念文档”和“操作文档”职责混杂

### 方案 B：新增两篇独立文档

优点：
- 文档职责清晰
- 读者可按阶段阅读
- 后续补充时不需要反复改动主指南

缺点：
- 文档数量增加
- 需要在结构上明确三篇文档之间的关系

**推荐：** 采用方案 B。  
原因：现有入门指南已经承担“体系认知”职责，继续追加实操内容会削弱它的清晰度。新增两篇独立文档更利于长期维护。

## 3. 文档设计

### 3.1 文档一：`llama.cpp` 常用命令速查

建议位置：

`/home/zj970/ai-study/KNOWLEDGE/Tools/llama.cpp-常用命令速查.md`

定位：
- 面向已经完成安装和环境配置的用户
- 提供高频命令的最小可用写法
- 帮助用户快速区分不同工具的用途和关键参数

拟包含结构：

1. 文档目的
2. 使用前提
3. `llama-cli` 常用命令
4. `llama-server` 常用命令
5. `llama-embedding` 常用命令
6. 常见参数速查
7. 常见使用误区

边界约束：
- 只写高频命令，不写全量参数手册
- 命令示例优先使用当前仓库已验证过的模型类型
- 每个命令只解释必要参数，不扩展成安装教程

### 3.2 文档二：本地知识库最小链路

建议位置：

`/home/zj970/ai-study/KNOWLEDGE/Tools/本地知识库最小链路-embedding-检索-回答.md`

定位：
- 面向已经理解 embedding 基本概念，但还不清楚最小链路如何串联的用户
- 解释“从文本到向量，再到检索，再到最终回答”的完整最小闭环

拟包含结构：

1. 文档目的
2. 最小链路总览
3. 第一步：文档切分与向量化
4. 第二步：问题向量化
5. 第三步：相似度检索
6. 第四步：把检索结果交给 chat 模型回答
7. 当前方案的边界
8. 下一步怎么演进到真正的 RAG

边界约束：
- 只讲最小闭环，不引入数据库、中间件或 Web 服务
- 重点讲清楚角色分工，而不是提供复杂工程实现
- 不把 embedding 文档写成 Python 项目脚手架

## 4. 文档之间的关系

三篇文档形成分层关系：

1. 入门指南  
   解决“`llama.cpp` 是什么”

2. 常用命令速查  
   解决“我现在应该敲什么命令”

3. 本地知识库最小链路  
   解决“embedding、检索、回答是怎么串起来的”

要求：
- 三篇文档互相补位，不重复展开相同内容
- 新文档如需引用概念，应尽量回指入门指南，而不是重新长篇解释

## 5. 写作原则

- 先给结论，再补原因
- 优先使用本轮已经验证过的真实命令形态
- 避免过度抽象，也避免过度工程化
- 对初学者最容易误解的地方，用“误区 / 易混点”单独指出
- 保持篇幅可控，确保读者能在一次阅读中形成完整理解

## 6. 风险与控制

### 6.1 风险

- 命令速查写成碎片化命令堆砌
- 最小链路写成纯概念说明，缺少可操作性
- 两篇新文档和入门指南重复过多
- 过早引入 RAG 生态名词，增加理解负担

### 6.2 控制策略

- 每个命令都标出用途和最少关键参数
- 最小链路文档坚持“角色分工 + 数据流”表达
- 新文档中不重复长篇解释 `GGUF`、量化、动态库路径等已有内容
- 明确写出“当前不覆盖什么”
