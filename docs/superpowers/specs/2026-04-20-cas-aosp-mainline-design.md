# `cas` 衍生 AOSP 实机开发主线设计说明

**目标：** 为 `Xiaomi Mi 10 Ultra / cas` 建立一条长期可推进的实机系统开发主线，在 `Arch Linux` 上完成衍生 AOSP 源码编译、真机刷机、回滚、`Framework` 动态调试和后续定制的任务设计。

**读者画像：**
- 已有 Android 系统编译、问题定位和部分 Framework 维护经验
- 想通过真实设备学习 AOSP / Framework，而不是停留在模拟器或只读源码
- 可接受刷机、清数据和反复回滚

**范围：**
- 锁定第一阶段 ROM 路线、Android 基线、调试模型、刷机策略和宿主机约束
- 定义第一里程碑的功能边界与验收标准
- 把整条主线拆成可执行阶段，写入现有学习任务体系

**非目标：**
- 不在第一阶段追求“日用机平替”
- 不做纯 AOSP 裸适配
- 不把自编 recovery、升级更高 Android 版本、相机/基带完善并入第一里程碑

---

## 1. 背景

用户当前已有一台已解锁 `bootloader` 的 `cas` 真机，系统仍为小米原厂系统。目标不是单次刷机，而是建立一条能长期支持：

- AOSP / 衍生 AOSP 编译
- 真机刷入验证
- Framework 代码动态调试
- 长期迭代与定制

的学习与开发主线。

当前宿主机为 `Arch Linux`，资源足够支撑 Android 源码编译；用户也明确希望尽量保持 Linux 闭环，而不是依赖 Windows 工具完成日常开发。

## 2. 关键决策

### 2.1 基线路线

采用 **衍生 AOSP 基线**，不做纯 AOSP 裸适配。

原因：
- 目标是“先建立稳定开发机”，不是先做设备 bring-up
- `cas` 公开社区存在可参考的设备栈与 ROM 维护锚点
- 能更快进入 Framework 学习和动态调试闭环

### 2.2 Android 基线

第一阶段锁定为：

- `LineageOS 21`
- `Android 14`

原因：
- 有明确公开维护锚点
- 成熟度和学习价值之间平衡更好

### 2.3 设备定位

设备作为 **专用开发机** 使用。

意味着：
- 接受清数据
- 接受多次刷机与回滚
- 不按“主力日用机”标准设计第一阶段任务

### 2.4 刷机与恢复策略

第一阶段采用：

- **recovery 优先**
- **先用社区现成 recovery**

不把“自编 recovery”作为第一阶段前置条件。

### 2.5 调试模型

第一阶段固定为：

- `userdebug`

原因：
- `adb root`
- 系统级调试属性
- Framework 验证链路

都更适合 `userdebug`。

### 2.6 系统形态

第一阶段选择：

- `GApps` 版

这会增加变量，但更接近用户希望的长期替代方向，因此在第一阶段直接纳入。

### 2.7 宿主机策略

采用：

- **纯 Arch Linux 闭环**

日常同步、编译、刷机、恢复和调试都按 Linux 设计，不把 Windows 工具纳入正式流程。

## 3. 第一里程碑定义

时间：
- `6-8` 周稳推

完成标志：
- 在 `Arch Linux` 上完成 `cas` 的衍生 AOSP 源码同步与编译
- 真机刷入成功并正常开机
- `adb devices`、`adb root` 正常
- 保留可执行的回滚路径
- 形成长期可重复的“改源码 -> 编译 -> 刷机 -> 验证”闭环

第一阶段必须正常的功能：
- 开机
- 显示
- 触控
- `USB`
- 充电
- 数据分区可正常使用
- `Wi-Fi`
- 蓝牙
- 音频
- `adb / adb root`

第一阶段不要求：
- 通话 / 短信 / 移动数据
- 相机
- 指纹
- `NFC`

## 4. 阶段设计

### 阶段 0：恢复安全网

- 固化设备当前系统与关键信息
- 准备官方 fastboot 固件作为回滚基线
- 准备社区 recovery 并验证 Linux 下可用性

### 阶段 1：源码与构建环境

- 固定源码目录、`out` 目录、`ccache`
- 同步 `LineageOS 21 / Android 14` 与 `cas` 相关设备栈
- 建立稳定 `lunch` 与编译入口

### 阶段 2：刷机闭环

- recovery 刷机
- GApps 集成
- 首次启动验证
- 失败回 recovery / fastboot 回滚

### 阶段 3：稳定开发机

- 验证开发必需功能
- 固化日志抓取和问题记录方式
- 保留稳定基线版本

### 阶段 4：Framework 最小调试闭环

- 选择低风险、小范围、可见性强的 Framework 改动
- 完成一次真机改动验证
- 证明设备进入长期调试状态

## 5. 风险与控制

### 5.1 风险

- 社区 recovery 维护状态不稳定
- `GApps` 增加首刷排障复杂度
- 纯 Arch 闭环削弱 Windows 兜底空间
- 设备功能诉求膨胀，导致第一阶段失控

### 5.2 控制策略

- 第一阶段只追“稳定开发机”，不追日用机
- recovery 虽优先，但仍保留官方 fastboot 固件作为回滚基线
- 若 `GApps` 阻塞首刷，先区分是否为系统基线问题
- 后续新增复杂目标时单独开子任务，不并入第一里程碑
