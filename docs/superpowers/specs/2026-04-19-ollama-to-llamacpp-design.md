# Ollama 全量移除并切换到 llama.cpp 设计说明

**目标：** 在 Arch Linux 本机上彻底移除 Ollama 及其模型、配置、缓存、服务残留，并建立一个可验证的 `llama.cpp` 本地推理环境迁移任务，采用源码编译安装，并支持 `NVIDIA GPU + CPU` 混合推理。

**范围：**
- 包含 Ollama 安装来源盘点
- 包含 systemd 服务停用与卸载
- 包含模型、缓存、配置和残留目录清理
- 包含 `llama.cpp` 的源码编译安装
- 包含 `CUDA` 后端构建与 CPU 参与的混合推理验证
- 包含最小可运行验证
- 不在本设计阶段直接执行系统修改

**非目标：**
- 不保留 Ollama 已下载模型
- 不兼容回滚到 Ollama
- 不覆盖图形界面前端、Open WebUI 等额外集成

---

## 1. 背景

当前机器已安装 Ollama，并配置了一系列模型。用户希望彻底移除现有 Ollama 体系，避免本地残留继续占用磁盘或干扰后续环境，同时改用 `llama.cpp` 作为新的本地推理方案。安装路线已经明确为源码编译，运行目标为 `NVIDIA GPU + CPU` 混合推理。

这个需求本质上不是“安装一个新工具”这么简单，而是一次本机 LLM 运行环境替换。任务如果直接写成几个命令，容易遗漏服务、模型目录、缓存文件、用户态配置或安装来源差异。为降低误删和漏删风险，需要先设计成分阶段迁移任务，再落到 `TASKS/todo.md`。

## 2. 方案选择

### 方案 A：极简执行

只记录几条卸载和安装命令。

优点：
- 最短
- 适合已经非常熟悉 Arch Linux 和 LLM 本地运行环境的人

缺点：
- 容易漏掉残留目录
- 出问题时难以判断卡在哪一步
- 不适合作为后续复用任务模板

### 方案 B：分阶段迁移

按“盘点现状 -> 停服务 -> 卸载 -> 清理残留 -> 安装 llama.cpp -> 验证”拆分成独立阶段，每阶段都有验证点。

优点：
- 风险边界清晰
- 适合当前需求
- 便于后续重复执行或复盘

缺点：
- 比极简方案更长

### 方案 C：原理教学型迁移

在分阶段基础上，额外解释 pacman、AUR、systemd、模型格式、GGUF、CUDA 和编译选项等背景知识。

优点：
- 学习价值更高

缺点：
- 会让任务清单过重
- 偏离“先完成迁移”的主要目标

**推荐：** 采用方案 B。  
原因：本任务既涉及系统清理，也涉及新环境建立。分阶段写法能同时兼顾执行稳定性和后续复用价值，同时能把 `CUDA` 构建和混合推理验证单独写清楚。

## 3. 设计

### 3.1 总体结构

最终写入 `TASKS/todo.md` 的任务采用一个独立任务块，名称暂定为：

`任务 9：彻底移除 Ollama 并切换到 llama.cpp`

该任务拆成 6 个阶段：

1. 盘点当前 Ollama 环境
2. 停止并禁用 Ollama 服务
3. 卸载 Ollama
4. 清理模型、配置、缓存和残留
5. 源码编译安装 `llama.cpp`
6. 运行 `NVIDIA GPU + CPU` 混合推理验证

每个阶段统一包含：
- 任务目标
- 执行步骤
- 验证方式
- 完成标准

### 3.2 阶段设计

#### 阶段 1：盘点当前环境

目的：
- 确认 Ollama 的安装来源
- 确认命令路径
- 确认服务状态
- 确认模型和配置目录

原因：
- Arch Linux 可能来自官方包、AUR、手工安装或脚本安装
- 不同安装来源会影响卸载命令

输出：
- 安装方式
- 服务状态
- 相关目录列表

#### 阶段 2：停止与禁用服务

目的：
- 防止卸载或删除目录时进程仍在占用文件

动作：
- 停止 `ollama.service`
- 禁用开机启动
- 检查是否仍有 Ollama 相关进程

验证：
- `systemctl status` 不再显示运行中
- 进程列表无相关进程

#### 阶段 3：卸载程序

目的：
- 从系统中移除 Ollama 命令和安装包

动作：
- 若来自 pacman 或 AUR，则使用相应包管理命令卸载
- 若来自手工安装，则删除对应二进制和启动脚本

验证：
- `which ollama` 无结果或命令不可用

#### 阶段 4：清理残留

目的：
- 彻底删除本地模型、缓存、配置、日志和用户级残留

重点清理对象：
- `~/.ollama`
- 可能的模型缓存目录
- 用户级或系统级 service 文件残留
- shell 配置中的 Ollama 相关环境变量或 alias

验证：
- 常见目录不存在或为空
- `systemctl list-unit-files` 中无 `ollama`

#### 阶段 5：源码编译安装 llama.cpp

目的：
- 建立新的本地推理运行环境

动作方向：
- 从 `llama.cpp` 官方仓库拉取源码
- 使用 `CMake` 执行源码编译
- 按官方文档启用 `CUDA` 后端
- 保留 CPU 参与计算的运行方式，而不是要求所有层都强制进入显存

验证：
- `llama-cli`、`llama-server` 或等价命令可执行
- 编译结果具备 `CUDA` 支持

#### 阶段 6：NVIDIA GPU + CPU 混合推理验证

目的：
- 证明迁移完成，不只是“命令装上了”

动作：
- 准备一个 GGUF 模型
- 用 `llama.cpp` 执行一次最小推理
- 使用运行参数验证 GPU 层卸载与 CPU 参与并存的路径

验证：
- 本地命令返回正常文本输出
- 日志中能看到 `CUDA` 设备被识别或启用
- 通过 `-ngl` 或等价参数控制卸载层数，验证并非纯 CPU 或纯 GPU 单一路径
- 若启用 server，可本地访问并返回结果

## 4. 风险与边界

### 4.1 风险

- 误删非 Ollama 模型目录
- 忽略用户 shell 配置中的残留环境变量
- Arch Linux 上安装来源不一致导致卸载命令错误
- `llama.cpp` 安装后缺少模型，导致用户误以为安装失败
- `CUDA` 工具链、驱动版本或显卡架构不匹配，导致编译或运行失败
- 对“GPU + CPU 混合推理”的理解不准确，误以为需要分别构建两套二进制

### 4.2 风险控制

- 清理前先盘点目录
- 任务中要求先列出待删除路径，再执行删除
- 任务中明确区分“程序已卸载”和“迁移完成”
- 最后必须有最小推理验证，而不是只看命令存在
- 单独加入 `CUDA` 可用性检查与 GPU/CPU 混合推理验证，避免只验证 CPU 路径或只验证编译成功

## 5. 测试与验收

最终任务的验收标准应至少包含：

- `ollama` 命令已不可用
- `ollama.service` 已停止、禁用并清理
- 旧模型、配置、缓存目录已删除
- `llama.cpp` 已通过源码编译安装完成
- `llama.cpp` 已启用 `CUDA` 后端
- 至少完成一次 `NVIDIA GPU + CPU` 混合推理测试
